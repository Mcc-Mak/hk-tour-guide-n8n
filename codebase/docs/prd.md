# 產品需求文件

本產品需求文件（Product Requirements Document, PRD）定義「香港建築物導賞手冊自動化流水線」的產品概述、功能清單、優先級排序、里程碑、發布計畫與風險評估，作為產品迭代與交付規劃的依據。

## 產品概述

### 產品定位

本產品為一套端到端自動化知識庫生成流水線，定位為「香港建築文化資產數位保存的基礎建設」。產品不追求互動式體驗，而是以批次、非同步、可追溯的方式，系統性地將零散的建築歷史資訊轉化為結構化、可信、可發佈的導賞手冊。

### 目標使用者

產品同時服務兩類使用者：一為終端讀者（觀光客、學生、研究員、導賞員），透過 mdBook 靜態網站消費導賞手冊；二為維運團隊（CrewAI 工程師、n8n 工程師、DevOps、專案經理），透過 n8n 工作流與 GitHub Actions 維運流水線。

### 價值主張

以「硬關卡真實性審查」建立可信度差異化優勢，以「CrewAI 多代理 + n8n 編排 + GHA 治理」實現規模化自動化，以「兩階段鷹架→生產」架構確保可控演進。產品核心價值不在於產出數量，而在於每份手冊的可信度與可追溯性。

## 功能清單

### 模組一：建築矩陣管理

- **F-001** 建築矩陣讀取 — 解析 `建築矩陣.md`，產出建築物清單（含分類、名稱、地址）。
- **F-002** 分類路由 — 依分類（法定古蹟／新界／市區）決定輸出路徑。
- **F-003** 建築物編號 — 為每座建築物指派 `{00001-99999}` 五位編號。

### 模組二：CrewAI 多代理研究

- **F-004** 歷史檔案研究 — `archival_researcher` 產出附來源的研究報告。
- **F-005** 硬關卡審查 — `credibility_assessor` 執行真實性判定。
- **F-006** 導賞手冊撰寫 — `documentation_writer` 產出 Markdown 手冊。
- **F-007** 專案經理同步 — `pm_agent` 更新 GitHub Issue 與 Project 看板。

### 模組三：n8n 工作流編排

- **F-008** Webhook 觸發 — 接收外部觸發啟動流水線。
- **F-009** 迭代迴圈 — Loop 逐建築物處理。
- **F-010** Execute Command — 呼叫 Python CrewAI 腳本並擷取 stdout。
- **F-011** 狀態載入 — 載入 runs JSON 供條件判斷與狀態檢視。

### 模組四：版本控制與 CI/CD

- **F-012** 自動提交推送 — 僅 stage 該輪產出，提交並推送至 `dev-001`。
- **F-013** 自動分支推進 — GHA 合併 `dev-001 → dev → main`。
- **F-014** 品質閘門 — CodeQL + SonarQube 掃描，零重大漏洞。
- **F-015** mdBook 部署 — 編譯靜態網站並自動部署。

### 模組五：可觀測性與治理

- **F-016** 中介狀態留存 — `step_callback` / `task_callback` 寫入 runs JSON。
- **F-017** CHANGELOG 自動更新 — 依變更級別調升語意化版本號。
- **F-018** 需求追溯 — RTM 映射需求至實作與驗證。

## 優先級排序

採用 MoSCoW 模型，並以「可信度 → 閉環 → 韌性 → 發佈 → 治理」為價值流順序：

| 優先級 | 功能 | 理由 |
| --- | --- | --- |
| Must | F-004, F-005, F-006 | 核心研究產出鏈，建立可信度 |
| Must | F-009, F-010, F-012 | 迭代迴圈與版本控制閉環 |
| Must | F-016 | 可觀測性確保可控 |
| Should | F-001, F-002, F-003 | 輸入管理 |
| Should | F-007, F-008, F-011 | 狀態同步與觸發 |
| Should | F-013, F-014 | 分支推進與品質閘門 |
| Could | F-015, F-017, F-018 | 發佈與治理 |

## 里程碑

### 里程碑 M1：鷹架產出（提示詞工作流）

完成第一階段提示詞工作流，產出 n8n 工作流 JSON、CrewAI 設定（agents、tasks、tools、config）、完整文檔集與 README。驗收：鷹架通過審查並推送至 `dev-001`，CHANGELOG 更新。

### 里程碑 M2：基礎設施就緒

完成 Docker Compose、自建 Dockerfile（含 Python、CrewAI、gh CLI）、`.env.example` 與 GHA 流水線水線檔案。驗收：`docker compose up` 可啟動 n8n 並存取 Web UI。

### 里程碑 M3：單座建築物閉環

於 n8n 中匯入工作流，以單座建築物觸發 Webhook，完成研究→審查→產出→提交→推送→狀態同步全流程。驗收：`dev-001` 出現該建築物提交，Issue 狀態同步完成。

### 里程碑 M4：批量迭代與韌性

以多座建築物驗證迭代迴圈，確認單座失敗跳過不中斷整體流程。驗收：Exception Log 正確記錄，跳過後續建築物正常處理。

### 里程碑 M5：CI/CD 與發佈

GHA 自動合併至 `main`，品質閘門通過後 mdBook 部署靜態網站。驗收：靜態網站可存取且內容正確。

## 風險評估

| 風險 | 影響 | 可能性 | 緩解策略 |
| --- | --- | --- | --- |
| LLM 產生無來源幻覺內容 | 知識庫可信度受損 | 高 | 硬關卡審查 + 最多五次嘗試（1 次初試 + 4 次重試）+ 跳過策略，嚴拒無來源內容 |
| 搜尋 API 配額耗盡 | 研究中斷 | 中 | 監控配額、`max_rpm` 限流、失敗跳過不中斷整體 |
| 建築矩陣資料不完整 | 部分建築物無法處理 | 中 | 跳過並記錄 Exception Log，後續補全 |
| n8n Webhook 主機不可達 | 流水線無法觸發 | 中 | 部署於可達主機，綁定 `0.0.0.0:45678` |
| GHA 品質閘門誤判 | 阻塞合併 | 低 | 掃描規則調校，零重大漏洞為準 |
| 直接推送至 dev/main | 破壞分支治理 | 低 | 分支保護規則 + 流水線自動合併 |
| LLM API 成本超支 | 財務負擔 | 中 | `max_rpm: 10` 限流、重試上限四次（共五次嘗試） |
| CrewAI 版本升級破壞相容性 | 腳本失效 | 低 | requirements.txt 鎖定版本範圍 |
