# 變更管理

本文件規範「香港建築物導賞手冊自動化流水線」的變更管理流程，涵蓋變更請求流程、分支策略、版本控制規範、提交訊息規範與 CHANGELOG 規範，確保所有變更可控、可追溯且品質受保障。

## 變更請求流程

### 流程步驟

1. **提出變更請求** — 於 GitHub 建立 Issue，標題簡述變更，內容說明動機、範圍與影響評估。標籤 `change-request`。
2. **影響評估** — 產品經理與工程負責人評估變更對需求（SRS）、設計（PDR/EDR）、API、資料結構與 RTM 的影響。
3. **決策與排程** — 依優先級（MoSCoW）排程，指定負責人與目標里程碑。
4. **實作** — 於 `dev-001` 分支實作，遵循分支策略與提交規範。
5. **驗證** — 更新 RTM 與對應文檔，確保需求可追溯。
6. **合併與部署** — GHA 自動合併至 `dev` 再至 `main`，通過品質閘門後部署。
7. **狀態同步** — 關閉 Issue，更新 Project 看板，記錄於 CHANGELOG。

### 變更分類

| 分類 | 範例 | 審核層級 |
| --- | --- | --- |
| 輕微 | 文檔錯字、配置調整 | 工程負責人 |
| 中等 | 新增工具、調整代理任務 | 產品經理 + 工程負責人 |
| 重大 | 架構變更、需求變更 | 專案發起人 + 全體審查 |

### 緊急變更

緊急修復（如流水線中斷）可加速流程，但仍須事後補齊 Issue、RTM 更新與 CHANGELOG 紀錄，確保可追溯性。

## 分支策略（dev-001 → dev → main）

### 分支職責

| 分支 | 職責 | 推送權限 |
| --- | --- | --- |
| `dev-001` | 建築物產出與功能開發的唯一推送目標 | 自動化流水線（`git_ops`）與開發者 |
| `dev` | 整合測試層，由 GHA 自動從 dev-001 合併 | 僅 GHA（嚴禁直接推送） |
| `main` | 發佈基準，由 GHA 自動從 dev 合併 | 僅 GHA（嚴禁直接推送） |

### 分支流動規則

- 所有提交（建築物產出、提示詞工作流產出、功能開發）一律推送至 `dev-001`。
- GHA 偵測 `dev-001` 推送後，自動以 `--no-ff` 合併至 `dev`，再合併至 `main`。
- 嚴禁任何人或腳本直接推送至 `dev` 或 `main`。
- 分支保護規則須啟用，禁止直接推送與強制推送（force push）。

### 建築物提交的分支行為

每座建築物完成後，`git_ops` 工具僅 stage 該建築物的產出檔案（導賞手冊 Markdown、CHANGELOG、runs JSON），提交並推送至 `origin/dev-001`。GHA 隨後自動推進至 `dev` 與 `main`。單座建築物的提交獨立，便於回滾。

## 版本控制規範

### 語意化版本號

CHANGELOG 遵從 [語意化版本號](https://semver.org/lang/zh-TW/)（`major.minor.patch`）：

| 版號變更 | 適用時機 |
| --- | --- |
| `major` | 不相容的架構變更（如更換多代理框架、變更資料結構契約） |
| `minor` | 新增功能或新增建築物手冊（向後相容） |
| `patch` | 錯誤修復、文檔修正、配置調整 |

### 版號調升規則

- 每座建築物或每輪提示詞工作流追加一筆 CHANGELOG 紀錄。
- 新增建築物導賞手冊 → 調升 `minor`。
- 修正既有手冊錯字或錯誤 → 調升 `patch`。
- 架構或需求重大變更 → 調升 `major`。
- 同一輪多筆變更，取最高級別調升。

### 版本標記

重大版本可於 `main` 分支以 Git tag 標記（如 `v1.0.0`），並由 GHA 觸發發佈流程。tag 命名為 `v{major}.{minor}.{patch}`。

## 提交訊息規範

### 建築物提交

每座建築物的提交標題固定格式：

```
feat(building): add biography and tour guide for {中文名稱}
```

body 須包含：

```
- 建築物編號: {building_id}
- 分類: {法定古蹟|新界|市區}
- 通過硬關卡審查，信心分數: {score}
```

### 提示詞工作流提交

提示詞工作流的提交標題格式：

```
feat(scaffolding): {簡述產出內容}
```

body 說明該輪產出的具體內容（如新增文檔、更新工作流等）。

### 其他提交類型

| 類型 | 範圍 | 範例 |
| --- | --- | --- |
| `feat` | building, scaffolding, pipeline | `feat(pipeline): add sonarqube scan` |
| `fix` | building, docs, crew | `fix(docs): correct path mapping` |
| `docs` | docs, readme | `docs(readme): add architecture overview` |
| `chore` | config, deps | `chore(deps): bump crewai to 0.72` |

### 提交規則

- 每座建築物一個獨立提交，僅 stage 該建築物產出，便於追溯與回滾。
- 提交標題為繁體中文（建築物中文名稱），類型與範圍為英文。
- body 簡明列點，說明變更內容與驗證狀態。
- 嚴禁於提交中包含金鑰或敏感資訊。

## CHANGELOG 規範

### 格式

CHANGELOG 採 [Keep a Changelog](https://keepachangelog.com/zh-TW/1.1.0/) 格式，並遵循語意化版本號。每個版本區塊以 `## [版本號] - 日期` 標題分隔，下列 `Added`、`Changed`、`Fixed`、`Removed` 等子分類。

### 紀錄規則

- 每座建築物完成後，於最新版本區塊的 `Added` 追加一筆（如 `- 新增 {中文名稱} 導賞手冊（{分類}）`）。
- 若新增版本區塊，須同時更新版號與日期。
- 修復既有手冊錯誤 → `Fixed`。
- 架構或設定變更 → `Changed`。
- 移除內容 → `Removed`。

### 範例

```
## [0.3.1] - 2024-10-15

### Added
- 新增 前九廣鐵路鐘樓 導賞手冊（法定古蹟）

### Fixed
- 修正 中央書院舊址 導賞手冊建築師資訊錯誤
```

### 維護責任

CHANGELOG 由 `git_ops` 工具於每座建築物完成後自動更新，並隨提交推送。手動變更（如架構決策）由開發者依規範撰寫。任何 CHANGELOG 變更須與實際提交內容一致，並反映於 RTM。CHANGELOG 為對外可見的變更歷史，須保持準確與簡明。
