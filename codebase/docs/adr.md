# 架構決策記錄

本文件記錄「香港建築物導賞手冊自動化流水線」的五項關鍵架構決策（Architecture Decision Records, ADR）。每項決策包含狀態、背景、決策、後果與替代方案，以確保技術選型的理由可追溯，並供未來決策者參考。

## ADR-001：採用 CrewAI 而非自定義 Agent

### 狀態

已接受（Accepted）

### 背景

本專案需要執行歷史檔案研究與真實性審查，涉及多個具備不同角色與工具的代理協作。團隊可選擇自定義手寫 Agent 框架，或採用現成的多代理框架。自定義方案雖然彈性高，但需自行處理代理間通訊、任務編排、記憶管理與重試邏輯，開發與維護成本顯著。

### 決策

採用 CrewAI 作為多代理框架。以聲明式 YAML 定義代理角色（agents.yaml）、任務（tasks.yaml）與設定（config.yaml），並以 Python 腳本由 n8n 的 `Execute Command` 節點呼叫執行。

### 後果

- 正面：降低代理協作的開發成本；提供記憶、重試、回呼等內建能力；社群與文檔支援充足。
- 正面：聲明式配置提升可維護性，角色與任務變更無需改程式碼。
- 負面：對 CrewAI 框架產生依賴，版本升級可能破壞相容性（以 requirements.txt 鎖定版本範圍緩解）。
- 負面：框架抽象層增加除錯複雜度（以 `step_callback` / `task_callback` 可觀測性緩解）。

### 替代方案

- 自定義手寫 Agent：彈性最高但開發成本過高，且本專案明確禁止。
- LangGraph：功能強大但偏向圖式編排，與本專案循序任務流程不盡契合。
- AutoGen：適合對話式多代理，但本專案需求為任務導向的研究與審查。

## ADR-002：n8n Docker 自架（Community Edition）

### 狀態

已接受（Accepted）

### 背景

本專案需要一個工作流引擎編排每座建築物的迭代迴圈，並以 Webhook 觸發。可選方案包含 n8n Cloud（託管服務）、n8n 自架 Community Edition（免費開源）、以及自建輕量編排腳本。n8n Cloud 為付費服務，且排程功能有限；自建腳本則缺乏視覺化與節點生態。

### 決策

採用 n8n Community Edition 自架於 Docker 容器，以 `docker-compose.yml` + 自建 `Dockerfile`（含 Python、CrewAI 依賴與 GitHub CLI）編排，綁定 `0.0.0.0:45678` 對外暴露。

### 後果

- 正面：永久免費、無供應商鎖定、可完全控制執行環境。
- 正面：自建映像檔可直接於容器內執行 Python CrewAI 腳本，免去跨容器通訊。
- 負面：需自行維運主機、備份與升級。
- 負面：Community Edition 無 Cloud 排程功能，故 Cron 排程移至 GitHub Actions。

### 替代方案

- n8n Cloud：免維運但付費，且排程與外部觸發受限。
- Apache Airflow：適合資料管線但過重，且缺乏 Webhook 即時觸發的輕量體驗。
- 自建 Python 編排：缺乏視覺化與節點擴充生態。

## ADR-003：分支流動 dev-001 → dev → main

### 狀態

已接受（Accepted）

### 背景

本專案為自動化流水線，每座建築物的產出需自動提交並經品質閘門合併至主幹。需選擇一個分支策略以平衡自動化效率與品質管控。直接推送至主幹風險過高；過多分支層級則增加複雜度。

### 決策

採用固定三層分支流動：每座建築物提交推送至 `dev-001`，GHA 流水線自動依序合併 `dev-001 → dev → main`。嚴禁直接推送至 `dev` 或 `main`。

### 後果

- 正面：自動化分支推進降低人工合併負擔。
- 正面：`dev` 作為整合測試層，`main` 作為發佈基準，職責清晰。
- 負面：三層流動增加合併延遲與潛在衝突。
- 負面：需嚴格的分支保護規則防止誤推。

### 替代方案

- 直接推送 main：風險過高，不符合品質閘門要求。
- GitHub Flow（單一主幹 + PR）：缺乏整合層，自動化合併粒度不足。
- GitFlow（feature/release/hotfix）：過於複雜，不適合自動化流水線。

## ADR-004：採用 mdBook 發佈靜態文檔

### 狀態

已接受（Accepted）

### 背景

本專案產出大量 Markdown 文檔（文檔集 + 導賞手冊），需以靜態網站形式發佈供終端使用者瀏覽。可選方案包含 mdBook、Docusaurus、Hugo、GitBook 等。

### 決策

採用 mdBook 編譯 Markdown 為靜態文檔網站，以 `codebase/toc.md` 作為 SUMMARY.md 格式的目錄樹，並透過 GitHub Actions 於品質閘門通過後自動編譯與部署。

### 後果

- 正面：mdBook 原生支援 Markdown，與本專案產出格式一致，無需轉換。
- 正面：輕量、無 JavaScript 框架負擔，行動裝置可讀性佳。
- 正面：CI/CD 整合簡單，單一二進位即可編譯。
- 負面：主題與客製化能力較 Docusaurus 有限。
- 負面：搜尋功能為基礎款，大量內容時需評估。

### 替代方案

- Docusaurus：功能豐富但需 React 與建置流程，與純 Markdown 產出風格不一致。
- Hugo：高效但主題與 Markdown 變體支援需調校。
- GitBook：付費且供應商依賴。

## ADR-005：硬關卡（Hard Gate）審查模式

### 狀態

已接受（Accepted）

### 背景

本專案的核心價值為內容可信度。若允許無來源或推測性內容進入知識庫，將損害學術與公眾教育價值。需選擇一個審查模式以確保品質。寬鬆審查可能放行錯誤內容；過嚴審查可能導致多數建築物被跳過。

### 決策

採用硬關卡（Hard Gate）審查模式：由 `credibility_assessor` 代理以不妥協標準審查，任何缺乏可驗證來源的事實陳述一律判定不通過。失敗時最多嘗試五次（1 次初試 + 4 次重試，退避 5 秒），仍未通過則執行 `fail-then-skip-building`，記錄 Exception Log 並跳過，確保知識庫純淨。

### 後果

- 正面：知識庫可信度最大化，符合學術與教育需求。
- 正面：跳過策略確保未通過內容不污染知識庫，同時不中斷整體流程。
- 負面：部分建築物可能因來源不足被跳過，覆蓋率下降。
- 負面：重試與跳過增加處理時間與 LLM 成本（以 `max_rpm` 限流緩解）。

### 替代方案

- 軟關卡（標示可信度分數但放行）：覆蓋率高但可信度受損，違背核心價值。
- 人工審查：品質最高但無法規模化，不符自動化目標。
- 僅一次審查不重試：效率高但 LLM 隨機性可能誤判，重試可提升通過率。
