# 使用者故事

本文件以敏捷開發的使用者故事格式，描述「香港建築物導賞手冊自動化流水線」的目標使用者、人物誌、史詩故事、使用者故事清單與驗收標準，作為需求工程與產品規劃的基礎。

## 人物誌

### 人物誌一：觀光客（陳小姐）

陳小姐為來自台灣的 28 歲旅客，計畫至香港進行三日文化深度遊。她具備中等程度的繁體中文閱讀能力，習慣在旅途中以手機查閱景點歷史背景。她的痛點是網路上的香港建築資訊零散、來源不明，難以判斷可信度。她期望能在一個結構清晰、內容可信的網站上，依地區瀏覽建築物的歷史故事與導賞路線，並在手機上離線閱讀。她重視內容的易讀性、實用性與移動端體驗。

### 人物誌二：學生（李同學）

李同學為香港中學中四學生，正修讀歷史科專題報告，題目為「殖民地時期的香港建築」。他需要可追溯來源的資料以撰寫報告，並希望理解建築風格與社會脈絡的關聯。他的痛點是學術資料庫門檻高、搜尋結果常缺乏結構。他期望導賞手冊提供結構化的建築資訊（興建年份、建築師、風格）與可引用的參考資料清單。他重視資料的正確性、來源可查證性與教育價值。

### 人物誌三：研究員（黃博士）

黃博士為大學建築史研究員，長期研究香港現代主義建築。他需要大量結構化、可程式化取用的建築資料以進行量化分析。他的痛點是缺乏統一格式的資料集，且各建築物的歷史資訊散落於不同機構。他期望本專案提供結構化的 JSON 研究中介狀態（`intermediate_research.json`）、可追溯的來源清單與穩定的 API 介面。他重視資料結構的嚴謹性、來源權威性與可重現性。

### 人物誌四：導賞員（梁先生）

梁先生為執業建築導賞員，每週帶領兩至三場市區建築導覽活動。他需要可直接用於現場導覽的腳本，包含建築特色、歷史軼事與建議路線。他的痛點是每次導覽前需花大量時間整理資料，且內容品質參差不齊。他期望導賞手冊提供模組化、可組合的導賞內容，並標示建築特色與導賞路線。他重視內容的實用性、路線合理性與現場可用性。

## 史詩故事

### 史詩一：自動化建築歷史研究

作為一個產品團隊，我們希望以 CrewAI 自動執行建築物歷史檔案研究，以便系統性地為大量建築物產出附來源的研究報告，免除人工逐一搜尋的成本。

### 史詩二：真實性硬關卡審查

作為一個歷史研究員顧問，我希望系統對每份研究執行硬關卡審查，拒絕無來源推測進入知識庫，以確保知識庫的可信度與學術價值。

### 史詩三：原子化迭代流水線

作為一個 DevOps 工程師，我希望 n8n 以原子化方式逐座處理建築物，單座失敗不中斷整體流程，以確保大規模處理的韌性與可恢復性。

### 史詩四：自動版本控制與部署

作為一個專案經理，我希望每座建築物的產出自動提交、推送並經 CI/CD 流水線合併至主幹，最終以 mdBook 部署為靜態網站，以確保流程閉環與即時發佈。

### 史詩五：可觀測性與狀態同步

作為一個專案經理，我希望透過 GitHub Project 看板與 Issue 狀態即時掌握每座建築物的處理進度，並能檢視 CrewAI 的中間思考記錄，以確保流程透明可控。

## 驗收標準

### US-001 驗收標準

- 導賞手冊依 `法定古蹟`、`新界`、`市區` 三大分類存放於對應目錄。
- mdBook 靜態網站提供分類導覽，使用者可點選分類瀏覽手冊。
- 每篇手冊檔名遵循 `{編號}-{中文名稱}-{中文地址}.md` 格式。

### US-007 驗收標準

- 每座建築物於 `codebase/.crewai/runs/{building_id}/intermediate_research.json` 留存結構化研究狀態。
- JSON 結構包含 `building_info`、`historical_context`、`architectural_features`、`cultural_significance`、`sources` 欄位。

### US-014 驗收標準

- 硬關卡審查失敗時最多嘗試五次（1 次初試 + 4 次重試）。
- 五次仍未通過時執行 `fail-then-skip-building`，於 `runs/{building_id}/` 記錄 Exception Log。
- 流水線繼續處理下一座建築物，不中斷整體迴圈。

### US-015 驗收標準

- 專案經理代理透過 `git_ops` 工具與 GitHub CLI 更新 Issue 狀態與 Project 看板。
- 每座建築物處理完成後 Issue 狀態同步為完成。

### US-016 驗收標準

- GitHub Actions 於 `main` 分支執行 CodeQL 與 SonarQube 掃描。
- 掃描要求零重大漏洞，通過後方執行 mdBook 編譯與部署。

### US-017 驗收標準

- 所有提交遵循分支流動 `dev-001 → dev → main`，嚴禁直接推送至 `dev` 或 `main`。
- 提交訊息遵循規範（`feat(scaffolding):` 或 `feat(building):`）並附 body。
- CHANGELOG 每筆變更追加紀錄並依級別調升語意化版本號。
